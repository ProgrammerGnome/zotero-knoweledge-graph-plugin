# Zotero Knowledge Graph Plugin

Zotero Knowledge Graph and Cloud-Based AI Analyzer

---

## 1. Introduction

### Development Objective

My goal with this project was to develop a plugin (client) for the Zotero reference manager, along with its associated serverless cloud backend. The system is capable of analyzing researchers’ literature collections (local articles), summarizing them using a Large Language Model (LLM), and identifying logical relationships between them (e.g., supports, refutes, extends). In addition, the system can retrieve new, relevant articles from the web through the OpenAlex API and integrate them into the existing Knowledge Graph.

### Main Functionalities (Functional Specification)

- **Local graph generation:** Automatic abstract extraction, summarization, and graph-based visualization of selected Zotero articles.

- **Web-based expansion:** Searching for related literature based on local seed articles (OpenAlex), analyzing them, and attaching them to the graph.

- **Visual representation:** Built-in HTML Canvas–based interactive graph and tabular view inside Zotero.

- **Automatic backup:** Cloud-based backup of the graph database state.

### Why Are Cloud and Advanced Database Technologies Necessary?

The Zotero client alone does not provide sufficient computational capacity to run heavy language models or efficiently store graph-based data.

- **Advantages of cloud technologies:** Google Cloud Run (Serverless) provides fast, asynchronous processing and API integrations (Gemini, OpenAlex) without overloading the client machine.

- **Database technology:** Instead of relational databases, using Neo4j (Graph Database) is essential because the true value of the information lies in the network-based relationships (edges) and their types between the data entities (articles).

## 2. Design and Architecture

### High-Level Architecture ("Boxes-and-Arrows")

### Cloud Services Used and Their Roles

1. **Google Cloud Run:** A fully managed, serverless runtime environment for the Node.js Express backend. It receives client requests and orchestrates API calls.

2. **Neo4j AuraDB:** A cloud-native graph database that stores articles as nodes and references as relationships.

3. **Google Generative AI (gemini-3-flash-preview):** Responsible for text understanding, summary generation, and extracting logical relationships between articles in JSON format.

4. **Google Cloud Storage (GCS):** Stores backups of the graph’s current state in JSON format.

### Logical Database Model

I applied the following schema in Neo4j:

- **Nodes:** Label: `:Article`, dynamically extended with either the `:Local` or `:Web` label depending on origin.
  - Properties: `id` (String, PK), `title` (String), `year` (String), `summary` (String), `origin` (String).

- **Relationships:** Directed connections between two `:Article` nodes.
  - Types: `EXTENDS`, `REFUTES`, `SUPPORTS`, `APPLIES`, `COMPARES`.

## 3. Implementation

During the project, I applied several non-trivial and advanced concepts related to both cloud computing and databases.

### Transaction Management (Transactional Control - Advanced DB)

Since the AI can occasionally return malformed responses during relationship extraction, implementing **Neo4j transaction management** was critical.

In the `index.js` backend, I open a transaction using `session.beginTransaction()`. Saving articles (Nodes) and relationships (Edges) happens as a single atomic operation. If the AI returns invalid JSON or the database throws a syntax error, the `await tx.rollback()` command reverts everything, preventing inconsistent data from being created.

### Data Sanitization and LLM Response Handling

The JSON output generated by Gemini frequently contained Markdown formatting (e.g., ` ```json `), while Neo4j enforces strict rules for relationship types (only alphanumeric characters allowed). I solved this in the backend with dynamic sanitization using `replace(/[^a-zA-Z0-9_]/g, '').toUpperCase()`.

### Logging and Automated Backups

- **Logging:** Instead of traditional `console.log`, I used the **Pino** module for structured JSON-based logging, which is ideal for integration with Google Cloud Logging.

- **Automated Backups:** I created a `/backup` endpoint in Cloud Run that queries the entire graph (nodes and edges) from Neo4j and exports it into a `.json` file stored in a dedicated **Google Cloud Storage** bucket. This endpoint can be automated for daily execution using **Cloud Scheduler**.

### Dynamic Labeling (Dynamic Cypher Query Generation)

To ensure data separation, the backend dynamically generates Cypher queries. Based on the `origin` parameter sent by the client, the MERGE operation is extended with either `SET a:Web` or `SET a:Local`. As a result, during visualization the GUI can easily distinguish (color-code) the different data sources.
